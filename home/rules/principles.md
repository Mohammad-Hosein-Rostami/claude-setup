# Principles for tools, hooks, CI and settings: P1-P16

Lessons of past review rounds (85 defects, 88 review notes), one row each, so a writer meets them while building; `from:` names
a sharpened part's past defect class. A brief names the ids that fit its files. They are plain design guidance: ask each question of your own change while you build; nothing is answered back at hand-off.

id | areas | principle | question to ask yourself
P1 | hooks, guards, anything run by a timeout | One total deadline below the hook timeout (a timed-out hook is cancelled, not blocked); each subprocess has a timeout that kills its process group; no super-linear regex on hostile text; a hostile file system (FIFO, link, /dev/zero, short read) fails closed (from: hook stalls, quadratic scans, orphans) | Does every read, regex and subprocess end before the hook timeout, and does a FIFO, link or short read deny, not hang or allow?
P2 | git in hooks and tools | Plumbing with pinned output flags (`-z`, full 40-hex shas), only in repos with provenance (a planted repo's config runs); copy proof is a verbatim patch-id plus merge-tree; land the tested sha, never a moving ref (from: planted repos, short shas) | Does each git call use plumbing, fixed flags, a full sha and a trusted repo, and land the tested sha?
P3 | gates and land | Fail closed on empty, missing or writer-reported gate input; an error is never read as empty, absent or passed; an exit-0 caller proves the CLI ran; a missing or failed agent report is incomplete; the aggregate lists failed members; no ignored result (C9) (from: errors read as nothing) | If this input is empty, missing, an error or the writer's, does the gate stop and show a failed member?
P4 | guards and permission exemptions | An exemption is a small allowlist grammar matched on the raw undecoded text; anything else asks | Is every exemption an allowlist on the raw text, so anything unlisted asks?
P5 | code reading branch names, subjects, file names or other untrusted text | Untrusted text is quoted, refused or capped before it reaches a command, a dialog or the context | Is every untrusted string quoted, refused or capped before a command, dialog or prompt uses it?
P6 | writers and readers of one store | The writer's size cap equals the reader's, both in bytes (from: string-length caps) | Do the writer and the reader of this store use one named cap in bytes?
P7 | locks, shared stores, temp names | Lock names, store keys and temp names are unique per run (own namespace); a release checks it still owns the lock, a stale break never takes a live holder, every tool mode takes the lock (from: lock steals) | Is every name unique to this run, and can a slow, killed or parallel run steal another's write?
P8 | tools with state or logs | Every write honours the --state-dir or --projects overrides; probes and tests never touch real state: an installer, hook or `claude -p` under test gets a temp HOME, USERPROFILE, TMPDIR and session id (from: a probe re-linked the live ~/.claude) | Do writes use the override, and tests a temp HOME, TMPDIR and session id?
P9 | retry loops, timers, nested waits | A retry on a timer backs off on any failure; a timed job longer than its tick never overlaps itself; nested waits sum to less than every outer timeout (from: overlapping sweeps) | Does each retry back off, can a slow run overlap the next tick, and do nested waits fit the outer timeout?
P10 | dialogs, prompts, defaults | Enter never acts as a click and a timeout is reported as a timeout; the owner's timed defaults go ahead marked as timed out; any other default taken for the owner is marked UNCONFIRMED | Does Enter refuse, is a timeout reported as one, and is each default marked UNCONFIRMED or timed out?
P11 | paths, branches, platforms | Environment facts: leads start in ~ (cwd proves no containment), MacBook and PC on macOS (PC slower, Node 22), Windows and Linux tested (drive paths), agent branches `worktree-agent-*`, APFS case-insensitive, /tmp a link (`realpathSync.native`), no TMPDIR = shared /tmp, bash 3.2 (from: case and temp-root defects) | Does the code hold for a start in ~, a drive path, an agent branch, a cased or linked path and the slower PC?
P12 | parsers, input, tests | Reuse the existing parser (C2); validate input with a schema (C10); no wall-clock asserts; each test fails without its fix: fakes act like the real dependency (cursor, case, errors, record shapes), text pins match whole clauses, one case leaves env knobs unset (from: vacuous tests) | Is the parser reused, the input validated, and would each test fail without the fix?
P13 | lanes relying on platform behaviour (hook events, CLI flags, git, shell) | The behaviour is probed and cited in the spec | Is each platform behaviour relied on probed, with command and result cited?
P14 | trust boundary | Name the boundary each input crosses (owner, agent, repo text, network); a writer's value or repo text never reaches a gate input, command line or path unvalidated; text shown to the model is data, not owner words; a child gets a minimal env, no secret in argv (from: digest injection, inherited tokens) | which inputs cross a boundary here, and where is each validated?
P15 | lifecycle symmetry | What install or a run adds (link, lock, temp worktree, record), uninstall, upgrade and every exit path remove or migrate; a removal touches only what lstat shows is ours, else backs up (from: an installer rm -rf) | for each thing this change creates, which code removes it on success, failure, crash and uninstall?
P16 | new state | New state reuses an existing primitive (session-store, session-lock, status rows) and names its stale, crash and old-reader cases; a pid alone is no identity; a JSONL reader survives a torn line (from: pid reuse, torn lines) | which primitive does it reuse; what if the record is stale, half-written or read by an older reader?

---
name: repo-restructure
description: Use when restructuring a whole repository - removing a build tool or layer (Nx, module federation, a monorepo tool), merging or moving apps and packages, deleting dead folders, scripts, plans or old configs, or rebuilding CI, Docker and deploy for a new layout.
---

Goal: the same product in a simpler layout. Nothing the owner did not name disappears, and every config still points at something real.

1. **Scope from the owner's words.** Write three lists to STATUS.md: delete (each path the owner named), keep (each exception they named), change. Anything else you want to delete goes on a fourth list, "proposed", with the proof that nothing uses it; ask before deleting it (`ask-owner`). Never widen a delete because a folder "looks unused".
2. **Safety net.** Start from a clean `git status` on a new branch. Tracked files move with `git mv` and go with `git rm` (history keeps them); one commit per step, so any step can be reverted alone. Files git does not track (env files, local settings, uploads) are never deleted or rewritten without the owner's yes: list them first (`git status --short --ignored`).
3. **Baseline before the first change** (one `runner` call, output saved to a file): install, typecheck, lint, unit tests (count), build (exit code and list of output files), dev server starts, `node ~/.claude/tools/refs/refs.mjs check .`, `node ~/.claude/tools/env-names/env-names.mjs list . --save <file>`. A check that already fails is recorded as failing, not fixed in passing.
4. **Inventory what the removed thing does**, one row each: what it does today -> what replaces it, or why it is dropped. Build tool (Nx, Turborepo): task targets and their order, caching, path aliases, lint boundaries, generators, per-project configs, CI commands. Module federation: remotes and exposes, shared singleton dependencies, remote URLs and their env variables, the async bootstrap boundary, how each remote deploys. A row with no answer is an open question, not a silent drop.
5. **Order.** Delete what is dead first (smaller surface); then move in batches of one package or folder, fixing aliases and imports in the same commit; then remove the tool; then root configs; then CI, Docker and deploy. After every batch: typecheck and `refs check`.
6. **Mine before deleting** old plans, notes and context folders: a `scout` lists what is still true and written nowhere else; durable facts go to the team's AI config or docs, then delete. Report what was kept, in one list.
7. **AI config clean-up.** Per tool (Claude, Cursor, Codex) one entry file and one place for rules; shared content lives once and the others point at it; no rule names a path, script or command that no longer exists (`refs check` covers links, grep the rest); nothing personal (`~/.claude`) in team files.
8. **Env and auth stay as they were** unless the owner says otherwise. Compare with `node ~/.claude/tools/env-names/env-names.mjs diff <file> .` (names only; never open or print an env file to compare). List where each of these is set and confirm it survived: auth redirect and callback URLs, cookie domain, CORS origins, API base URLs, base path, ports, feature flags.
9. **Sweep for leftovers** with hidden folders included (plain `rg` skips `.github`, `.cursor`, `.claude`): `rg --hidden -g '!.git' -g '!node_modules' -i "<removed tool, old folder names, old aliases>"`. Each hit is fixed, or listed with the reason it stays. Regenerate the lockfile; run `knip` for unused files and dependencies.
10. **CI, Docker, deploy** follow I1-I6 and are validated without deploying (`docker build`, `docker compose config`, `actionlint` and `hadolint` when installed). Registry, hosts, secrets, domains and the first real deploy are the owner's decisions: ask.
11. **Old cached pages, before the first deploy.** When a build layer is removed, list the entry files a browser with a cached old page still requests: remote entries (`remoteEntry.js`), old chunk paths, service worker, manifest. Decide per file: keep a stub that reloads the page, redirect, or accept the 404 (say why). Check the HTML's cache headers (`no-cache` on the entry page, long cache only on hashed files). Verify with a cold load from an old cached page, not a fresh tab.

Done-gate: every baseline check re-run and compared (the test count is lower only by the suites the owner asked to delete, listed); `refs check` exits 0; `env-names diff` shows only changes the owner approved; the leftover sweep is clean; an old cached page loads after the deploy; the app starts and its main flows open; the "proposed" list is answered. Report: deleted, moved, kept on purpose, not verified.

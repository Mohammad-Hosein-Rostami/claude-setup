# How this setup works (no AI needed to read it)

This repo configures Claude Code: the rules it follows, the helper programs it runs, and the small scripts that watch
what it does. Everything is plain text and Node scripts. You can read, change and switch off any part by hand.

## What each folder holds

| Folder | What is in it |
| ------ | ------------- |
| `home/` | The content that gets linked into `~/.claude`. Editing a file here changes every running session at once. |
| `home/CLAUDE.md` | The short global instructions every session reads (language, who does what, questions, git, safety). |
| `home/rules/` | One-line rules, each with an id, that apply to matching file paths (`paths:` in the frontmatter). |
| `home/standards/` | The longer reference behind the rules, with examples (for human readability: `readability.md`). |
| `home/skills/` | Step-by-step workflows (`<name>/SKILL.md`) that Claude loads when the task matches. |
| `home/agents/` | The agents (lex, dev, tess, max and their helpers), one file each, with their model, effort and preloaded skills. |
| `home/project-notes/` | Shared notes, one file per project; personal notes live in `personal/project-notes/`, which `~/.claude/project-notes` links to. |
| `personal/` | Your own layer, git-ignored and its own git repo, made by the installer from `personal.example/`: `CLAUDE.md` (your rules), `project-notes/`, `share-deny.txt`. |
| `home/hooks/` | Node scripts Claude Code runs on events (after an edit, at session start, when a question waits, ...). |
| `home/tools/` | Command-line tools with their own README (`ui-check`, `ui-coverage`, `land`, ...). |
| `settings/` | `base.json` plus one file per OS. They are merged into `~/.claude/settings.json`. |
| `plugins/` | The list of plugins to install. |
| `tools/` | System programs to install (`Brewfile`, `windows-tools.ps1`); not the same as `home/tools/`. |
| `scripts/` | `install.sh` and `install.ps1` (they call `install.mjs`), `share-check.mjs`, `sync-machines.mjs` and `lane-new.sh`. |
| `tests/` | The test suite (`node:test`), run by hand. |
| `docs/` | The documents for people. `catalog.md`, a list of everything, is generated by install and git-ignored. |

## How one prompt flows

1. You start Claude with `claude --model <m> --effort <e>`. The main session is the boss.
2. Claude reads `home/CLAUDE.md`, your `personal/CLAUDE.md` and the rules whose paths match the files it works on.
3. The boss hands the work to `lex` (plan), `dev` (build), `tess` (tests, reviews and test writing) or, rarely, `max` (the ship
   agent: it prepares a release or deploy and stops), at most 3 of each at once. Each agent file lists its model, tools,
   preloaded skills and the helpers it may start. Only the boss starts lex, dev, tess and max (no other agent does): an agent that
   needs one asks the boss with a `needs:` line. lex works only for the boss, so a `needs: lex` always goes to the boss.
4. The boss works in rounds. lex's plan comes with `<plan>.pieces.json`: small pieces, each with its feature, its files and
   the pieces it must wait for. After every agent report and every land the boss runs `board tick`
   (`node ~/.claude/tools/board/board.mjs tick --repo <main checkout> --plan <pieces.json>`). For each piece that can start,
   while fewer than 3 dev run, it claims a folder from the lane pool (`git-tidy lane claim`) and gives it to dev; no agent
   makes its own folder. When dev reports, the boss lands the piece with the `land` script, one at a time, and ticks again to
   check main. Each land frees a slot, which the boss fills at once.
5. Agents have full access: commands run with no permission prompt, and no hook checks a command first. A dangerous `rm` runs
   without a prompt too, because the installer sets `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1` in the shell start-up
   files (restart Claude Code from a new terminal to pick it up). Nothing stops a delete, so agents follow the rule "Look
   before deleting or overwriting" in `home/CLAUDE.md`. A question for you is Claude Code's own terminal question;
   left unanswered it auto-continues after 5 minutes with no keypress and Claude takes the recommended option. The timer
   does not count down while that terminal window is focused, so to let it run, switch to another window or app.
6. After each edit, `post-edit.mjs` runs the project's formatter.
7. Tests, type check, lint and reviews run on main, one feature at a time, by the table "Which tess work a change gets" in the
   `qa-plan` skill (`home/CLAUDE.md`, "Quality checks", sums it up): dev's report names the change's risk
   (`node ~/.claude/tools/risk/risk.mjs`). By default tess does a quick look: the tests the change touched, a type or syntax
   check, and one read of the diff against the brief and its acceptance lines. A risky change lands, then gets that quick
   look on main at once, the boss tells you its risk in one line, and no new piece touches its files until tess returns;
   other code changes get it when 3 features have landed unchecked or the job's last piece has landed; docs and text only
   get none. The heavy checks (`full`: the whole suite, edge cases, a deep review, new tests, long checks) run only when you
   ask for them in chat, and what you ask for runs at once. Nobody tests or edits in the main folder: it is
   only where the boss lands, and it keeps moving. Each tess tests its own feature in a snapshot lane, a lane detached at
   main's commit (`git-tidy lane claim --snapshot --base <sha>`), released after it returns. A full suite (only in `full`) runs once per
   commit; its result is kept in `<git common dir>/cs-suite/<sha>.txt` and the other tess reuse it. tess answers
   `main: ok` or `main: must-fix <n>`; the boss re-checks a must-fix on the newest main, then makes it a new piece, and
   tess-write's new tests land like any other piece. dev and its helpers run no tests; tess
   hands the runs to `tess-run` (full suites, installs and builds run directly, a full suite once per tree), and in `full` edge cases to `tess-edge`, the simplicity review to `tess-simple`, a review to `tess-review` and
   missing tests to `tess-write`, and keeps the verdict. No check runs by itself when an agent stops; no hook calls the risk
   command.

When a change makes a feature that uses Claude work for the first time, dev names a `smoke:` line (a command and what it
should show) and `tess` runs it 1 to 3 times with real Claude, recording each try; nothing waits for it. After 3 rounds of fix
and review on one area, the boss sends the area to `lex` for a redesign instead of patching again. Locks, concurrency,
security and data-loss work goes to `lex` for a short state design before the build.

The hook list with exact triggers is in `docs/catalog.md` (section Hooks, generated by install) and `home/hooks/README.md`.

## Virtual lanes

A lane from the pool is a git worktree in `<repo>/.claude/worktrees/lane-<n>`. On macOS with APFS it is filled by cloning
the main checkout file by file with `cp -c`: the copy shares the disk blocks with the main checkout until a file changes, so
a lane holds the whole project, `node_modules`, `.env` and build output included, at almost no disk cost. Nested repos,
other worktrees and Python venvs are skipped, and the claim fails unless `git status` in the lane is clean. git still finds
what a dev changed, and `land` still puts it on main. Local secret files such as `.env` are deleted when the lane is
reclaimed. Where cloning is not possible (another file system, Linux without reflink, Windows) a lane is made as before, and
`GIT_TIDY_LANE_FILL=checkout` turns cloning off. Why: `docs/adr/0011-virtual-lanes.md`.

## The UI checks

Nobody labels UI work. `node ~/.claude/tools/ui-proof/ui-proof.mjs plan` reads the request (the brief, which quotes your words),
the diff and the screens the diff reaches, and returns the check plan, whose depth fits the change (rules:
`home/standards/ui-checks.md`):

| Depth | When | Proof |
| ----- | ---- | ----- |
| none | only tests, docs pages or dev config changed | nothing |
| same | dependencies only, or a "no visual change" request | renders before and after are identical |
| render | logic, text or look on a screen with no design | renders before and after: no new problem; logic also needs its tests |
| visual | a new screen or state (no render before), or a screen with no url to open | the `dev-pixel` compare loop and the `pixel-qa` final gate |
| pixel | a design word or Figma link in the request, or a look change on a screen with a Figma frame | the full pixel-perfect path, unchanged: `figma-pixel-perfect`, `ui-check run` rounds until every state passes, then the `pixel-qa` final gate on the tree that lands |

Evidence only raises the plan: a brief line `UI-PLAN: <depth>` can make it stricter, never lighter, and what cannot be read takes
a stricter path. `ui-proof check --plan` checks the proof of a plan; there are no waivers. Old problems on both sides are
printed as `follow-up:` lines; new ones fail the check.

## Status line

`home/statusline.mjs` prints the status line, and `home/tools/board/lib/render.mjs` draws its rows. Every row has an example
in `home/tools/board/README.md`, which also holds the row layout, the colours and the refresh. Besides that:

- There are no job, now, step or estimate rows and no `/where` tree (plan 2026-11-24).
- Colour goes by kind (RC14): branch names green, bars and their counts cyan, durations and clocks blue, session values
  grey-violet.
- The cells are ASCII under `CLAUDE_STATUS_ASCII=1`, `TERM=dumb`, the old Windows console or a non-UTF-8 locale. There is no
  colour under `NO_COLOR`, `TERM=dumb` or the old Windows console.
- It reads only cache files: no git and no transcript. What it writes, what it starts and what it prints on an error are in the
  header of `home/statusline.mjs`.

## Where each kind of rule lives, and how to change one

| You want to change | Edit | Then |
| ------------------ | ---- | ---- |
| A rule every session follows | `home/CLAUDE.md` (keep it short) | none |
| A rule for some file types | `home/rules/<area>.md` (`paths:` in the frontmatter) | none |
| The long explanation of a rule | `home/standards/<area>.md` | none |
| How an agent behaves | `home/agents/<name>.md` (its frontmatter `description` is its catalog row) | none |
| A workflow | `home/skills/<name>/SKILL.md` (its frontmatter `description` is its catalog row) | none |
| A permission or hook wiring | `settings/base.json` (or the OS file) | run `scripts/install.sh` to rebuild `~/.claude/settings.json` |

Edit in a git worktree (a pool lane from `git-tidy lane claim`, or `scripts/lane-new.sh <name>`), not the main checkout: the
files are live in every session. Land by rebasing onto main and fast-forwarding (`git merge --ff-only`), through the `land` script (`--test "<command>"` tests the rebased tip first). Details: `CLAUDE.md` (this repo's
own rules) and `docs/usage.md`.

## Turn a hook off by hand

- One hook, until you re-run the installer: open `~/.claude/settings.json`, find the `command` that names the script
  (for example `post-edit.mjs`) and delete that entry from its `hooks` list.
- One hook, for good: delete the same entry from `settings/base.json` and run `scripts/install.sh`.
- Some hooks have a switch: `CLAUDE_POST_EDIT_SKIP=format` (or `all`) skips the formatter.

## Run the tests

From the repo root:

    node --test tests/*.test.mjs

Never run bare `node --test`. The `ui-check` tool has its own tests: `npm run test:ui-check` (`npm run test:all` runs both).

No test runs by itself: a commit and a push run none, and `land` runs one only with `--test`; the boss sends changes to
`tess` by the table "Which tess work a change gets" in the `qa-plan` skill. Run the whole suite, or one file
(`node --test tests/principles.test.mjs`), when you want to know that everything still works, or ask `tess` to.

## Install on another machine

    git clone <repo> ~/Desktop/claude-setup && cd ~/Desktop/claude-setup
    scripts/install.sh --dry-run        # preview
    scripts/install.sh                  # macOS, Linux, Git Bash

On Windows use `powershell -ExecutionPolicy Bypass -File scripts\install.ps1`. Existing files are moved to
`~/.claude-backup-<stamp>/`, never deleted. Put machine-only settings in `settings/local.json` (copy
`settings/local.json.example`). To check the result, ask `tess` for a setup check. Full steps: `docs/setup.md`.

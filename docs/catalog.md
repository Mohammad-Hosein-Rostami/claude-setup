Routing policy (which tier does what) is in `home/lead-rules.md` (injected into the lead session by `session-notes.mjs`): the Opus session leads and delegates. `general-purpose` (no `model`) runs on Sonnet 5.5 via `env.CLAUDE_CODE_SUBAGENT_MODEL`; the built-in Explore agent gets `sonnet` and Plan `opus` from `agent-model-guard.mjs`, otherwise they run on the lead's model; precedence is the Agent call's `model`, then frontmatter, then that env var.
`architect`, `reviewer` and `security-auditor` have `memory: user` (notes in `~/.claude/agent-memory/<name>/`); `reviewer` and `security-auditor` stay read-only for project files through the `agent-memory-only.mjs` hook in their frontmatter.

| File | Event | What it does |

| `pre-bash-guard.mjs` | PreToolUse(Bash|PowerShell) | Blocks nothing for good. A command with a hit that a rewrite fixes (a variable command word, a risky word inside shell expansion, a literal secret) is first bounced back once with the fix (a deny the agent reads, outcome `bounce`); the bounce also names every other reason that will still ask after the rewrite, and the identical command sent again gets the dialog. Otherwise a rule hit (git `--no-verify`, force push incl. `+refspec`, `rm -rf` outside the project or of a whole folder (the working directory, or a bare glob such as `*`, `./*`, `.*` of it, the project root, home, a temp root or `/`; a bare glob below a bare glob, `./**/*` or `*/*`, counts the same; an `rm -r` target over 4096 characters is not read and asks), disk wipes, literal secrets, `git push`, `gh release`, `gh pr merge`, package publish, writes to production hosts from `~/.claude/private/prod-hosts`) opens a timed dialog: Allow by default, no answer in 2 min (max 190) goes ahead, Deny on click; Allow and timeout print no decision (normal permission flow and deny rules still apply); no GUI or a failed dialog falls back to the CLI prompt. Quality rules (a hand-edited lockfile, a `git merge` or `git pull` that can create a merge commit, a branch moved by plumbing: `git update-ref refs/heads/<x>` or `HEAD`, a ref in a variable, `update-ref --stdin` setting anything but a literal ref outside refs/heads/ (HEAD, `%s`, `$REF` count), `branch -f`, `push|fetch . a:<branch>`, `fetch -u <any repository> a:<branch>`; `update-ref -d` and literal refs outside refs/heads/ stay silent; git itself already refuses `branch -f` and a plain `fetch|push .` onto a branch checked out in any worktree) get advice instead: denied once with the fix, the identical command sent again runs, no dialog. A wait by sleeping (a `for`/`while`/`until` loop with `sleep` of 5 s or more, or one `sleep` of 30 s or more, `lib/wait-advice.mjs`) gets the same once-advice: run it with `run_in_background: true` and `timeout` (the expected run plus a margin, at most 7200000 ms = 2 h) and wait for it inside the turn; a call already sent with `run_in_background: true` gets none; shorter sleeps and quoted or heredoc text never count. Every git global option is read, so none can hide a guarded subcommand. Commands git itself runs (`lib/git-runs.mjs`: `rebase -x`, `bisect run`, `submodule foreach`, `-c core.pager=`, clone's `-c`, `git config` writes, `alias.*`, `GIT_SSH_COMMAND` and the other variables git runs, `ext::` and `git remote-ext`) get the same rules as a `bash -c` body; what git runs that the guard cannot read asks "git runs a command this guard cannot read" (a `--config-env` variable not set in the line, `ext::` switched on, and, next to a dangerous word, config files or values set through `printf -v` or other variables). Git's own programs (`git-push`, `<exec path>/git-rebase`) count as `git <sub>`, `git config` values after `--` are read, and the value of a variable git runs is checked wherever the line assigns it (`lib/git-run-values.mjs`; one it cannot read, such as `$(...)`, asks the same unless it is one reference like `"$EDITOR"`). Command names ignore case on macOS and Windows, as their file systems do; a variable assigned from a backtick is unknown, as after `$(...)`. Destructive hits say `DESTRUCTIVE:`. Logs decisions to `~/.claude/logs/guard.jsonl`; Bash writes to code files are logged by `bash-writes.mjs`. Scans every word of a command for these rules (so `ionice -c3 rm -rf /x` and `$'\x72m'` are caught); `eval` of a variable or substitution asks. A second character-level parser (`lib/shell-lexer.mjs`) is a raw-text backstop, and a fail-to-ask rule (`lib/raw-risk.mjs`) asks whenever a hidden-execution construct (`$(`, backtick, `<<`, `<(`, `eval`, `trap`, `case`) meets a dangerous word anywhere in the raw text (a commit message and the single-quoted argument of echo, printf, grep, rg, jq, sed without `e`/`w`/`-i` or `git log` without `--output` are data, `lib/inert-arguments.mjs`; data piped to a shell, a file writer or out of a group, a line that writes any file, a `$'...'` word, `${`, `case`, `eval`, a function or `PATH=` still asks); a command over 32 KB asks "command too long to check"; `| bash`, `bash <<EOF`, a variable command word, `env -S`, `su -c`, `git -c alias.*`, `gh api` writes and `diskutil erase` ask. Anything it cannot parse is allowed. Unquoted brace words are expanded as bash does and a split unquoted variable is judged word by word; a look-alike command name or a brace word it cannot list asks. It is a tripwire, not a sandbox (README Limits). It never fails open on its own errors: a failure in its code after the rules asks ("guard error: <error class>", logged as `guard-error`), and `"onFailure": "block"` on its entry in `settings/base.json` blocks the call when the hook dies or times out. The host list and the decision log are opened through `lib/plain-file.mjs` (no waiting, no link followed, regular files only, a size cap): a host list that is there but is not a plain file makes every ssh, scp, rsync, psql and mysql write ask. Hook input it cannot read (not JSON, no string `command`) asks "the guard could not read its input" instead of letting the call run. A command is judged from every folder the line's `cd`s may have led to (`lib/cd-folder.mjs`): a `cd` is believed alone only inside its own `&&` chain (also inside `( )`, `{ }` and `if`, and across a pipeline between two `&&` that holds no `cd`); where it may or may not have taken effect (after `;`, a newline, `||`, `&`, a pipe, the end of a group or compound, behind `!` or a wrapper such as `sudo`) the folder before it and the one after are both judged, and a relative `rm -r` target, a bare glob or a `find` start folder runs unasked only when it is fine from every one of them (4 at most). The folder is unknown, and a relative `rm -r` target asks, with more than 4 possible folders, for a relative `cd` in a loop or a function body, after `eval`, `source` or `.`, for `cd +N`, a bare drive, a relative `cd` under `CDPATH`, and after `setopt autocd` or `shopt -s cdable_vars`; an absolute `cd` makes it known again inside its own chain, except after a `cd`, `pushd` or `popd` whose own target could not be read (that unknown is final for the line). Judging a segment in more than one folder is paid from the line's work budget, so scripts nested in scripts after `cd`s cannot multiply the guard's work: over the budget the line asks `command too complex to check`. Each branch of a zsh glob group in an `rm -r` target (`(*|.*)`) is judged as a target. An `rm` whose option word holds an expansion (`-$X`, `"$@"`, `"${a[@]}"`, a leading `$F`) is judged as recursive; its reason says "rm that may be recursive", not "rm -r". A `find` reason shows a line break in its target as a mark, as the `rm` reasons do, and the hook's answer to input it cannot read has its own reason class (`guard input unreadable`). One work budget for the whole line (`MAX_LINE_READINGS` in `lib/rm-paths.mjs`): over it the guard asks "command too complex to check" instead of working without bound. |

## Status line
